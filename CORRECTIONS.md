# Corrections policy

Report a possible error through a GitHub issue without including personal medical information.

Material factual, safety, retraction, or interpretation errors are handled immediately:

1. verify the report against the primary source or registry;
2. publish a patch edition such as `2026.08.1`;
3. describe the correction in the new edition changelog;
4. keep the original edition intact; and
5. attach a visible correction notice to every affected historical edition.

Typographical changes that do not alter meaning may be bundled into the next review, but they must still appear in version control.

Website presentation and deployment defects use the existing research edition number when the approved evidence record itself is unchanged. Examples include a template failing to render an existing section, stale deployment output, broken navigation, styling, or accessibility markup. The repair must:

1. leave the edition data, evidence wording, review date, and translation record unchanged;
2. be recorded in version control;
3. pass checks against the built and live page, not only the source data; and
4. add a visible service or correction notice when the defect may have misled readers.

Do not create a patch edition merely because the website failed to display already-approved content. If the repair changes evidence selection, interpretation, patient-facing wording, source links, reviewed hierarchy encoded in the research record, or translation content, use the applicable research or translation version process instead.

The project will not erase an old claim merely because it became outdated. Historical snapshots remain available with a prominent superseded or correction notice and a link to the replacement edition.
